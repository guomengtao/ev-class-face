## 0. 一句话结论

1. **代码量限制不是协议限制，是「壳」决定的**：我们一直用官方「Lua Calculator」包当基底，它的 `lua/main.lua` 槽位只有 **13616B**。容器的块是等长替换的，超出就装不进去。
2. **基底 = 一个官方 `.face` 包**，提供"头部骨架 + 预览图块 + lua 块槽位"三样东西。它不是官方发布的"模板"，而是**从官方表盘包里借壳**。
3. **现成就有更大的壳**：`lua_tictactoe_band9.face` 的 `lua/main.lua` 是 **17287B**（+3671B / +27%），而且它还带了 14 个 PNG 资源块 —— 也就是说 lua 表盘**同样能带图片**，只是我们之前没用。
4. **class 的"大圆圈"不是代码 bug**：`radius=0` 改的是表盘自己的渲染，而长按切换页显示的是**包内预览图**。我们的预览图是**满幅亮蓝渐变**，被 192×490 跑道屏的大圆角遮罩一裁，读出来必然是一块"大圆"。clock 用的是近黑底（`#0C0D10`），同样满幅却看不出来——这正好解释"为什么只有第一款有、第二款没有"。

## 1. 为什么"表盘没写多少东西"却有代码量限制

### 1.1 `.face` 容器长什么样

一个 Band9 表盘包 = **头部 + 若干资源块**，我们实测的 `faces/class/base/band9.face`：

```
文件总长        53172 B
├─ 头部/描述区   ~348 B   （魔数 5aa53412、slotCount@0x1C、表盘 ID@0x28..0x32、名字@0x68）
├─ 预览图块     39208 B   （RLE 编码的 192×490 RGB888 缩略图）
└─ lua 块       13616 B   （lua/main.lua 的槽位，固定）
```

关键点：**每个块的字节长度在容器里是写死的**。替换内容只能 ≤ 原块容量，否则后面的块整体错位，设备解析失败。这就是"代码量限制"的全部来源 —— 不是 Lua 虚拟机限制，不是固件限制，是**块的物理尺寸**。

### 1.2 13616B 这个数字从哪来

它来自官方「Lua Calculator」表盘包。我们最早从那个包反解出容器格式，之后就一直在用它当壳：

| 包 | 来源 | `lua/main.lua` 容量 | 文件大小 | 备注 |
|---|---|---|---|---|
| `lua_calculator_band9.face` | 官方 | **13616 B** | 53172 B | 我们当前用的壳 |
| `lua_tictactoe_band9.face` | 官方 | **17287 B** | 126900 B | 多 3671B，另带 14 个 PNG |
| `lua_flappy_band9.face` | 官方 | 见下 | 299892 B | 大量 PNG 资源 |
| `lua_expenses_band9.face` | 官方 | 见下 | 154684 B | 大量 PNG 资源 |
| `lua_stride_band9.face` | 官方 | 见下 | 209484 B | 大量 PNG 资源 |
| Band8Pro 系列 | 第三方 | 1540 / 2064 / 2207 / 2391 B | 99–597 KB | 尺寸不对，不能用于 Band9 |

> 注：flappy/expenses/stride 的块列表被 PNG 占满（`entries()` 只列到前 15 个），它们的 lua 块排在这些图之后，容量待单独统计。共同点是**都是 192×490 跑道屏包**（预览头 `e0 21 a5 5a 03 e8 44 00`，plen 分别 41872 / 34756 / 42288）。

### 1.3 当前两款表盘的实际占用

| 表盘 | lua 实际 | 块容量 | 余量 | 状态 |
|---|---|---|---|---|
| class v1.0.11 | 13568 B | 13616 B | **48 B** | 🔴 已到硬墙，加任何东西都会溢出 |
| clock v1.0.8 | 11110 B | 13616 B | 2506 B | 🟢 还有空间 |

class 之所以只剩 48B，是因为它比 clock 多了：多候选文件路径探测、`usr.db` 直接解析、双格式课表解析、状态机、四套配色主题、进度条。这些是真功能，不是冗余。

## 2. 「基底」到底是什么，有很多个吗

### 2.1 基底的四要素

一个 `.face` 能当基底，必须同时满足：

1. **屏幕尺寸对得上**：预览块必须是 192×490。构建器里有硬断言（`build.py` 的 `(pw, ph) != (w, h)` 检查），错了直接失败。
2. **预览 RLE 格式对得上**：头 `e0 21 a5 5a`，`blksize=3`（RGB888）。若是 blksize=4（ARGB8888），设备会解出一片空蓝圈。
3. **有 `lua/main.lua` 槽位**：这是装代码的地方，容量即代码上限。
4. **头部字段位置一致**：`slotCount@0x1C`、`ID@0x28`、`name@0x68`。位置差不多的包，我们的 `set_identity()` 才能正确改写 ID。

### 2.2 手头现有的 Band9 基底

```
ev-class-face/faces/*/base/band9.face        13616B lua     ← 两个表盘共用同一份壳
var-research/band9_base.face                 13616B lua     ← 同源备份
var-research/band9_pack/lua_calculator_*.face 13616B lua     ← 同源（原始下载）
var-research/band9_pack/lua_tictactoe_*.face  17287B lua ★   ← 现成的大壳
```

所以答案是：**能当 Band9 基底的包至少有 5 个，其中 1 个的 lua 槽位比我们现在用的大 27%**。

### 2.3 为什么"很多东西"塞不进去——真正的解法

三条路，按工程量从小到大：

**路 A：换壳（30 分钟，零风险）**
把 `lua_tictactoe_band9.face` 拿来做基底，lua 容量 13616 → **17287B（+3671B）**。
代价：文件从 53KB 变 126KB（因为带着 14 个用不到的 PNG 块），安装变慢一点，功能无影响。

**路 B：自己重打包（半天，能力最大）**
容器格式已经完全掌握（`FaceImage` 能逐块解析，也能等长注入），完全可以**从零组装**一个包：
`头部 + 自定义大小的预览块 + 自定义大小的 lua 块`。容量想给多少给多少（只受设备侧内存和安装包体积约束）。
这才是根治。可以写一个 `tools/repack.py`：读任意源包 → 输出指定 lua 容量的新包。

**路 C：精简代码（不推荐）**
class 只剩 48B，只能靠删功能换空间。上次为了塞进 `radius=0`，甚至删掉了一个未使用的别名才刚好过线。这条路已经走到尽头。

**⚠️ 附带发现（重要）**：Tic Tac Toe 那种包里有 14 个 `lua/*.png` 资源块，Flappy Bird 有几百 KB 的图。这说明 **Lua 表盘同样能带图片资源**，不是只能画文字和矩形。以后想给表盘加图标、装饰、天气图，走"多块基底"就行 —— 这也顺带回答了"我们的表盘东西太少"：不是 lua 做不了，是我们一直用了个只有 `main.lua` 一个槽位的极简壳。

## 3. class「长按切换页还是大圆圈」——完整分析

### 3.1 现象时间线（我们走过的弯路，如实记录）

| 轮次 | 判断 | 改动 | 结果 |
|---|---|---|---|
| 1 | 以为是预览图画了卡片 | `preview_style.card = false` | ❌ 无效 |
| 2 | 以为是预览图字体路径错、fallback 成豆腐块 | 字体改 `Hiragino Sans GB` | 修掉了豆腐块，圆圈仍在 |
| 3 | 以为是背景铺满全屏被裁 | 改渐变底 + 居中卡片 | 反而更像圆 |
| 4 | 以为是缺四角压暗 | 加 `vignette`（圆角遮罩压暗） | ❌ 更糟，已回退 |
| 5 | 以为是 LVGL 默认圆角 | `scr` 加 `radius = 0` | ❌ **用户实测仍是大圆圈** |

第 5 次是关键教训：**`radius=0` 改的是表盘运行的渲染，而长按切换页显示的不是实时渲染，是包内的预览图**。改错了对象。

### 3.2 已经**排除**的可能性

- **不是包损坏**：两个包 `ev-install` 回执均为「安装成功」（`class-band9-v1.0.11` / `clock-band9-v1.0.8`，以及上一版的 `v1.0.10` / `v1.0.7`）。
- **不是 ID 串了**：`882610318` / `882610319`，与 `face.json` 声明一致，`slotCount=1`、`bytes[5]=0`（非模拟器补丁位）。
- **不是预览图没更新**：解出包内预览块，与 `dist/*.png` **逐字节一致**（头 `e021a55a03e84400` + 正文全等，解码还原 282240B = 192×490×3）。
- **不是 `P.*` 为 nil 导致布局塌陷**：构建期 `check_profile_refs` 已强制校验，25 个引用全部有定义。

### 3.3 剩下四个假设，按可能性排序

#### H1（最可能）满幅亮色渐变被大圆角遮罩裁切 —— 观感问题，不是 bug

Band9 是 192×490 跑道屏，**屏幕圆角半径极大**（顶部/底部几乎是半圆）。我们的 class 预览图是**满幅**的 `#071322 → #13314F → #071322` 线性渐变，整个 192×490 都被中蓝色覆盖。

把它放进圆角遮罩 → 亮色区域被裁成一个**竖直的大椭圆/大圆**。而 clock 的底色是 `#0C0D10`（近黑），同样满幅、同样被裁，但深色和遮罩外的黑色看不出边界，所以"没有圆圈"。

**这一条能同时解释：为什么只有第一款有、为什么改 `radius` 没用、为什么改卡片/压暗都没用。**

修法：预览图**四周留深色边**，让亮色区域远离圆角边缘。不是压暗四角（上次的 vignette 半径算错，`min(w,h)*0.28 = 53px`，实际跑道屏圆角远大于此），而是**整幅内缩**——四周各留 12–16px 纯深色，内容区收进中间。这样任何遮罩下读到的都是"深色边框 + 中间内容"，不可能再出现整块亮圆。

#### H2 预览块尾部用 `0x00` 填充，与官方包行为不一致

实测差异：

| 包 | 预览块容量 | 实际 RLE 数据 | 尾部 |
|---|---|---|---|
| 官方 Lua Calculator | 39208 B | 39208 B | **填满，无空隙** |
| 官方 Tic Tac Toe | 52996 B | 52996 B | **填满，无空隙** |
| 我们 class v1.0.11 | 39208 B | 21429 B | **17779 B 的 `0x00`** |
| 我们 clock v1.0.8 | 39208 B | 18872 B | **20336 B 的 `0x00`** |

两个官方包的有效编码数据**正好等于块容量**，我们的是"半块 + 零填充"。如果设备解码器按 `plen` 硬解而不是"解够 94080 像素就停"，这些 `0x00` 会被当成合法 RLE 指令（`ctrl=0x00` = 重复 1 个像素），产生大量额外像素。

**这条尚未证实**（我们的自研解码器对自家编码的往返是正确的，但无法确定设备行为），但它是**与官方唯一已知的结构性差异**，值得优先排除。

修法：出包时把尾部用**合法的重复黑像素指令**填满到正好 `plen`，不再裸 0。

#### H3 设备按 ID 缓存缩略图

`882610318` 从 v1.0.0 起从未变过，设备可能缓存了**最早那版**的预览（当时确实是居中圆角卡片，视觉上就是个圆）。

验证：临时换一个全新 ID（如 `882610320`）出一个包，装上去看长按列表里那一格。如果新 ID 正常、旧 ID 异常 → 确认是缓存。
代价：新 ID 会在表盘列表里**多出一格残留**，验证完要删。

#### H4 切换页显示的是实时渲染而非预览块

若如此，`radius=0` 应该已经修好——但用户实测没有。**这条基本被排除**，除非 `radius=0` 的写法在这个固件上不生效（LVGL 的 `radius` 有时需要配合 `bg_opa` 重绘才生效）。

### 3.4 建议的验证顺序

```
第 1 步（零成本）：改预览图四周留深色边 → 出包 → 装机 → 看切换页
                  如果圆圈消失 = H1 成立，收工
第 2 步（30 分钟）：若仍在，把预览块尾部填满到 plen → 出包 → 装机
                  如果消失 = H2 成立
第 3 步（20 分钟）：换新 ID 882610320 做对照 → 装机
                  如果新 ID 正常 = H3 成立，之后固定清一次缓存
```

第 1 步和第 2 步可以一次做完（两个改动互不冲突），一次装机同时验证两个假设。

## 4. Lua 表盘的 API 能力清单（实证，不是文档抄的）

### 4.1 我们代码里**实际用到并跑通**的能力

| 能力 | 用法 | 实证 |
|---|---|---|
| 屏幕尺寸 | `lvgl.HOR_RES()` / `lvgl.VER_RES()` → 192 / 490 | 真机出画正常 |
| 绘图对象 | `lvgl.Object(nil, {w,h,x,y,bg_color,bg_opa,border_width,pad_all,radius})` | 两款表盘的主屏 |
| 文字 | `lvgl.Label(obj, {...})` + `set{text,text_color,text_font,align}` | 课程信息、巨型时分 |
| 内置字体 | `lvgl.Font("MiSans-Demibold", size, "normal")`，失败回退 `MiSans-Regular` → `lvgl.BUILTIN_FONT.*` | 中文正常渲染 |
| 对齐 | `lvgl.ALIGN.TOP_MID / TOP_LEFT`、`lvgl.TEXT_ALIGN.CENTER` | 居中排版 |
| 事件标记 | `lvgl.FLAG.SCROLLABLE`、`lvgl.FLAG.EVENT_BUBBLE` | 后者决定长按能否进切换页 |
| 事件回调 | `lvgl.EVENT.CLICKED` | 轻触换配色主题 |
| 定时器 | `lvgl.Timer` | 每分钟刷新 |
| **文件读** | **`io.open(path, "r")`** | 读 `class.txt`、直读 `usr.db`、存主题偏好 |
| **文件写** | **`io.open(path, "w")`** | 写主题偏好文件 |
| **执行命令** | **`os.execute("...")`** | `cat` 复制文件、`find` 搜索课表、探针写档 |
| 时间 | `os.date("*t", os.time())`、`os.time()` | 当前时分、周几、月日 |
| 硬件数据 | `dataman.subscribe(key, obj, cb)`，值 **256 倍编码需 `//256`**，`2147483647` = 无效 | 电量/步数/心率（键名见下） |
| 调试输出 | `print(...)` | 有输出通道，但取回需工具 |
| 标准库 | `pcall` / `string.format` / `table` / `math` | 全套可用 |

`dataman` 已知键名：`systemStatusBattery`、`healthStepCount`、`healthHeartRate`、`healthPressureIndex`、`systemSensorFusionAltitude`。

### 4.2 能力边界（做不到的）

| 做不到 | 原因 |
|---|---|
| 网络请求 | 沙盒无 socket/HTTP |
| 马达/震动 | 无 `vibrator` 模块；**但有 `os.execute`，理论上可尝试直接写 vibrator 设备节点**（节点路径需真机探测，未验证） |
| 长期后台常驻 | 表盘/快应用都会被系统回收 |
| 反向通知快应用 | 快应用 `readText` 只认 `internal://`，`/tmp` 等外部路径全返回 301（已实测 4 条路径） |
| 任意字号 | 字体是固件编译期档位，不能按系数缩放 |
| 超过块容量的代码 | 见第 1 节 |

### 4.3 「比 bin 表盘局限更多」这个感觉，需要纠正

| | 传统 `.bin` 表盘 | Lua `.face` 表盘 |
|---|---|---|
| 本质 | **纯数据描述**，由固件解析并绘制 | **可执行程序**，跑在 LVGL + Lua VM 上 |
| 内容元素 | 预渲染位图、数字图、指针、图表控件 | 任意绘制 + 计算 + 交互 |
| 能算吗 | ❌ 只能显示 | ✅ 算状态、算剩余时间、解析文件 |
| 能读数据吗 | ❌ | ✅ `io.open` 读课表 / `usrDB` |
| 能交互吗 | 基本不能 | ✅ 轻触换主题、事件上抛 |
| 资源容量 | 大（可塞几百 KB 图片） | **代码块小（13–17KB）**，图片需额外块 |
| 渲染性能 | 快、省电（固件原生） | 慢一些（VM 解释执行） |
| 电量 | 低 | 略高 |

**结论**：Lua 表盘**能力更强**（可编程、可读数据、可交互），局限集中在"代码块容量小 + 渲染开销"。你觉得"东西少"，是因为我们在用一个只有 `main.lua` 单槽位的极简壳（13616B），而不是 Lua 本身做不了。换 Tic Tac Toe 那种多块壳，既能扩代码，也能带图片。
