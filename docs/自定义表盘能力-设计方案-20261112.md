# EV Class 表盘 · 自定义外观与布局能力设计方案

> 日期：2026-11-12
> 范围：`faces/class`（小米手环 9 跑道屏 192×490，Lua 表盘）
> 状态：背景图已实现并实测通过；组件开关 / 槽位 / 纯色渐变背景为本次设计

---

## 1. 一页结论

要做的事可以归成一句话：**把表盘从「固定布局」改成「读配置文件决定长什么样」**。

```
手机 App（编辑外观）  --MessageApi-->  快应用（写 cfg.txt / bg.png）  -->  表盘（读盘渲染）
```

三件事的难度差很多，必须分开排期：

| 能力 | 技术难度 | 阻塞点 | 判断 |
|---|---|---|---|
| 用户上传背景图 | 低 | 只剩传输通道 | **已通**（表盘侧实测） |
| 纯色 / 双色渐变背景 | 极低 | 无 | 直接做，纯 LVGL 属性 |
| 组件开关（时间/日期/状态/课程/进度条） | 低 | 无 | 直接做，读 cfg 决定建不建 |
| 5 槽位自定义位置 | 中 | 布局重排算法 | 做，但要限定槽高与溢出策略 |
| 动画背景 | **高** | 无 Canvas/Line、内存 | **不建议首版做**，见 §6 |

## 2. 已实证的事实（不是推测）

来自 probe 表盘在 Vela 模拟器上的实测回传：

```
EV_PROBE v1.0.0  obj=OK label=OK image=OK angle=OK pivot=OK
                 img_src=OK anim=OK line=NO canvas=NO
                 fs_wr=OK img_abs=OK
EV_PROBE_DIR  /data/quickapp/files/com.application.watch.classschedule/  79
```

- `img_src=OK` + 截图中白方块内渲染出红块 → **`Image:set{src=包外绝对路径}` 真实解码绘制**
- `fs_wr=OK` → Lua `io.open` 可写快应用数据目录
- `line=NO` / `canvas=NO` → **没有矢量绘制能力**，这条直接否掉了「渐变/图形靠代码画」
- `anim=OK` / `angle=OK` / `pivot=OK` → 指针类动画可行

未验证（真机固件可能与模拟器不同）：

1. 真机上表盘进程是否同样有权写快应用目录（写不了也不致命，快应用代写即可）
2. `MessageApi` 单包上限（80KB 图能否一次传给快应用）
3. 快应用不常驻：传图前必须先唤醒

## 3. 配置协议：`cfg.txt`

### 3.1 为什么不用 JSON

Lua 沙箱没有 `json` 库；手写 JSON 解析器至少 200–300 字节 Lua 源码，而 class 表盘只剩约 2KB 容量（lua 压缩后 15283B / 上限 17287B）。**逐行 `key=value` 二十行内能解析完，且天然容错**。

### 3.2 文件位置（按序探测，先命中先用）

```
/data/quickapp/files/com.application.watch.classschedule/cfg.txt
/data/quickapp/files/cfg.txt
/tmp/cfg.txt
```

与 `bg.png` 同目录，同一套探测逻辑 —— 少一份代码，少一处不一致。

### 3.3 字段表

| 键 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `bg_mode` | `image` / `solid` / `gradient` | image | 图片 / 纯色 / 纵向渐变 |
| `bg_color1` | `0xRRGGBB` | `0x000000` | solid 主色；gradient 顶部色 |
| `bg_color2` | `0xRRGGBB` | `0x1E3A52` | gradient 底部色 |
| `dim` | 0–100 | 45 | 图片背景压暗强度 |
| `show_time` | 0/1 | 1 | 时间 |
| `show_date` | 0/1 | 1 | 日期（无课时填充课程名行） |
| `show_status` | 0/1 | 1 | 状态行（上课中/课间/下节） |
| `show_subj` | 0/1 | 1 | 课程名 |
| `show_next` | 0/1 | 1 | 下一节信息 |
| `show_bar` | 0/1 | 1 | 进度条 |
| `show_info` | 0/1 | 0 | 诊断两行（默认关，普通用户不需要） |
| `slot1`…`slot5` | 见 §4 | 见 §4 | 五个纵向槽的内容类型 |
| `c_time` | `0xRRGGBB` | `0xFFFFFF` | 时间色 |
| `c_accent` | `0xRRGGBB` | `0x7FD4FF` | 强调色（状态/进度条） |
| `c_sub` | `0xRRGGBB` | `0xFFD479` | 次要信息色 |
| `y1`…`y5` | 整数 | profile 值 | 槽位纵坐标，App 端「位置微调」写入 |

**缺字段 = 用默认值**：没有 `cfg.txt` 时表盘行为与旧版**完全一致**，这是硬要求（老用户零感知）。

## 4. 槽位模型（5 个位置）

跑道屏 192×490，可视安全区 y≈96–394，共 298px。切 5 槽，每槽 56px + 余量：

| 槽 | 默认内容 | 默认 y | 槽高 |
|---|---|---|---|
| slot1 | `time` | 102 | 52 |
| slot2 | `status` | 154 | 30 |
| slot3 | `subj` | 184 | 40 |
| slot4 | `next` | 282 | 28 |
| slot5 | `bar` | 314 | 6 |

槽内容类型（`kind`）：

| kind | 渲染 | 字号 |
|---|---|---|
| `time` | 时钟，44px 粗体 | 44 |
| `date` | `11/12 周三` | 30 |
| `status` | 上课中 / 课间 / 距下节 | 28 |
| `subj` | 课程名（≤6 字换行截断） | 30 |
| `next` | 下一节 `高数 8:00` | 24 |
| `bar` | 课程进度条 | — |
| 空串 | 该槽不显示 | — |

**设计约束（不做就会翻车）**：

1. **槽高固定、字号随槽高降档**。用户把 44px 的时间塞进第 5 槽（y=314）会压住进度条，所以创建时按 `槽序号 → 字号表` 降级，而不是用 kind 自带字号。
2. **`y1`–`y5` 只做 ±40px 的微调**，不允许任意值。手环屏幕小，自由摆放必然出现重叠；限制范围后，App 端滑动条也能做成「微调」而不是「画布」。
3. **`bar` 槽占 6px，其余槽最小 24px**。App 端要按此校验，不允许把 bar 放进 slot1 还配大字号。

「5 个位置」这个数量是对的：再多，192px 宽的手环上每块只剩 20px，字都放不下。

## 5. 背景三模式

| 模式 | 实现 | 备注 |
|---|---|---|
| `image` | 满屏 `Image{src=bg.png}` + `dim` 黑色遮罩 | 已实现；无图自动回落纯黑 |
| `solid` | `scr:set{bg_color=bg_color1}` | 零成本，纯属性 |
| `gradient` | LVGL 原生 `bg_grad_color` + `bg_grad_dir=VER` | **需实测该固件是否支持**；不支持则退化为 solid（不算失败） |

三条共同要求：

- 任何模式下文字都必须可读 → 深色背景下白字 + 强调色；亮色背景必须自动加 `dim`
- 切模式不改 z 序：`Image` 与 `dim` 层始终先于文字创建
- 装饰件一律 `clear_flag(CLICKABLE)` + `EVENT_BUBBLE`，否则长按进不去表盘切换页（已踩过）

## 6. 动画背景：为什么建议首版不做

三种可能的实现，都不划算：

| 方案 | 问题 |
|---|---|
| 多帧 PNG 定时切换 | 每帧 192×490 ≈ 20–80KB，10 帧就是 0.8MB，手环存储与内存都吃不住；且 `line/canvas=NO`，无法用代码生成帧 |
| LVGL `anim` 对单个 Image 做位移/缩放 | `anim=OK`，但那是**对象属性动画**（指针旋转用过），做不出「背景流动」的观感；缩放会露底 |
| 纯色呼吸/渐变扫动 | 只能靠动画改 `bg_color`，成本低但视觉信息量极低，用户新鲜感一天就没了 |

**结论**：动画背景是「看起来高级、实际收益最低、风险最高」的一项。如果一定要有动态感，性价比更高的是**进度条推进动画**和**秒级指针**——已有 `anim=OK` 支撑。

这个判断有前提：手环 RAM 未知。如果实测 80KB 图解码后内存余量很大，多帧方案可以重新评估。

## 7. App 端（手机）需要什么

最小可用界面，一个页面：

```
┌─ 表盘外观 ────────────┐
│  [预览 192×490]        │  ← 用同一份 cfg 在手机上渲染预览
│                        │
│  背景  ○上传图 ●纯色 ○渐变
│  颜色  [■] [■]   压暗 ──●── 45%
│                        │
│  ☑ 时间  ☑ 状态  ☑ 课程名
│  ☑ 下一节 ☑ 进度条 ☐ 日期 ☐ 诊断
│                        │
│  位置  时间 ──●──── 102
│        状态 ──●──── 154
│        ...             │
│                        │
│      [ 应用到手环 ]     │
└────────────────────────┘
```

关键点：

1. **预览必须用同一份 cfg 渲染**，不能是另一套模板 —— 否则「手机上调好、手环上不一样」，这是这类功能最常见的投诉。
2. **上传图在手机上预缩放到 192×490 PNG**，表盘绝不做缩放（内存）。
3. **「应用」= 一次原子写**：先写 `bg.png.tmp` + `cfg.txt.tmp`，校验后 rename。半包会导致白屏。
4. 传输前必须**先唤醒快应用**，并把「快应用未运行」做成明确提示，而不是静默失败。

## 8. 分期路线

| 期 | 内容 | 验收 |
|---|---|---|
| P1 | `cfg.txt` 解析 + 组件开关 + 纯色/渐变背景 | 无 cfg 时行为与旧版一致；改 cfg 后开关生效 |

P1/P2 只动表盘，不依赖手机端，现在就能做。P3/P4 才需要改 App 和快应用。

## 9. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 槽位自由摆放导致重叠 | 文字叠字，不可读 | y 限 ±40px 微调 + 槽高字号降档 |
| 用户传亮色照片 | 白字看不清 | 强制 dim 下限（image 模式 dim 不低于 30） |
| 大写 PNG 解码 OOM | 表盘崩溃 | App 侧预缩放 + 表盘只读 8 字节判签名 |
| 传图时快应用未运行 | 静默失败 | 唤醒 + 明确报错 |
| 真机写盘权限比模拟器严 | 图落不了盘 | 快应用代写；表盘只读 |
| cfg 解析崩溃 | 整个表盘白屏 | 全字段 `tonumber` 兜底 + 缺省值，非法行跳过 |

## 10. 与官方的差异（定位）

官方的自定义表盘支持更完整的图层编辑（元素级拖拽、多图层、字体选择）。本方案是**简化版**：

- 不是画布，是**5 个固定槽位 + 内容类型选择**
- 不是任意颜色，是**三档配色 + 三种背景模式**
- 不做动画背景

理由：手环 192px 宽 + 无 Canvas + 内存受限，做「半个官方编辑器」的成本远高于收益；能用、不易配错、手机上一分钟调完，才是这个尺寸设备该有的形态。
