# 从 .face 包内解出预览块 · 做法与可靠性评估

> 日期：2026-11-12　适用：小米手环 9 / 10 / 10 Pro（192×490 等）Lua 表盘
> 结论先行：**这是一个可靠的「结构体检」手段，不是一个可靠的「效果预览」手段。**
> 它能百分百回答「设备会不会把缩略图显示成大圈」；它不能回答「盘面在手腕上长什么样」。

---

## 一、这个手段解决的是什么问题

表盘长按切换页里，每个表盘有一张缩略图。这张图**不是设备实时渲染 lua 得到的**，而是包内自带的一块 RLE 位图，固件解码后直接贴出来。

所以当这块数据有问题时，出现的是**结构性故障**，不是视觉瑕疵：

- 缩略图变成一个**大圆圈 / 占位图形**（就是我们昨天修的那个 bug）
- 或者干脆空白、花屏

这类故障用截图对比、看配色、调圆角都不可能修好，因为根因在字节层。**唯一能定位它的办法就是把这块数据按固件的方式解一遍**，看解出来的像素数对不对。

排查时最忌讳的是「换 ID 试试」「换预览图试试」——本仓 `docs/表盘技术边界与class大圆圈分析-20261111.md` 里那套「圆角裁切 / 安全区」的解释就是错的方向，文首已加勘误。

---

## 二、原理：预览块在包的哪个位置

`.face` 是定长容器，头部有固定偏移表（`shared/face_container.py`）：

| 偏移 | 含义 |
|---|---|
| `0x00` | 魔数 `5a a5 34 12` |
| `0x05` | 模拟器补丁标记（官方为 0，出包前必须清） |
| `0x1C` | 槽位数 slotCount |
| `0x20` | **尾部预览块偏移指针 tail_offset** |
| `0x28` | 表盘 ID（10B） |
| `0x68` | 表盘名（24B） |
| `0x110..0x200` | 资源条目表，16B/条（3B size + 1B namelen + 16B reserved + name + content） |

拿到 `tail` 之后，预览块自身的布局是：

```
tail + 0x04   u16 宽  (192)
tail + 0x06   u16 高  (490)
tail + 0x08   u32 槽位长度 plen
tail + 0x0C   8B  官方 RLE 头，原样保留
tail + 0x14   RLE 流，长度 = plen - 8
```

RLE 流本身极简（`shared/rle.py::decode`）：

- 控制字节 `c == 0` → 结束
- `c & 0x80` → 重复：接下来 `c & 0x7f` 个 3 字节像素块，整体重复该次数
- 否则 → 字面：接下来 `c` 个 3 字节像素块，原样输出
- 像素格式：**RGB24，3 字节/像素**，行优先，尺寸取头部 w×h

解码结果的字节数除以 3 就是像素数，和 `w*h` 一比就知道对不对。

## 三、一条命令解出来

```python
import sys; sys.path.insert(0, '.')
from shared.face_container import FaceImage
from shared import rle
from PIL import Image

p = 'dist/Band9/Band9-Aurora-v1.0.15.face'
im = FaceImage(p)
w, h, plen = im.preview_meta()                       # 192, 490, 31164
body = bytes(im.data[im.tail + 20: im.tail + 20 + plen - 8])
px = rle.decode(body)                                # RGB24 原始像素
Image.frombytes("RGB", (w, h), px[:w * h * 3]).save('/tmp/preview.png')
print(w, h, len(px) // 3, "期望", w * h, "余", len(px) // 3 - w * h)
```

实测输出（v1.0.15，正常包）：

```
192 490 94080 期望 94080 余 0
```

一张图就到手了，不需要开模拟器、不需要连手环、不需要装机。

## 四、三个真实样本，三种读数

| 包 | 头部尺寸 | 解码像素 | 比值 | 流/槽位 | 余B | 判定 |
|---|---|---|---|---|---|---|
| `Band9-Aurora-v1.0.15.face`（按 `encode_exact` 出包） | 192×490 | 94,080 | **1.00** | 31,156/31,156 | 0 | ✅ 正常 |
| `Band9-Daymatter-v1.0.0.face`（官方底包） | 192×490 | 94,080 | 1.00 | 52,996/52,996 | 0 | ✅ 正常 |
| `Band9-Aurora-v1.0.1.face`（上一轮手搓包） | 读成 49152×59904 | **0** | **0.00** | 1/7,977,977 | — | ❌ 坏 |
| `Analog v1.0.8`（旧 `pad_to` 出包） | 192×490 | 1,223,239 | **13.00** | — | — | ❌ 坏 |

坏包有两种形态，都很典型：

1. **表头就是错的**（v1.0.1）：宽高读成 49152×59904、槽位近 8MB、解出 0 像素。这说明预览块的表头与长度字段压根没按结构写，容器拼错了——不是「像素多了几倍」，是块本身不成立。
2. **像素灌水**（13.00 倍）：旧 `pad_to()` 为了填满槽位，用重复指令硬凑，每 4 字节多解出 127 个**假像素**。设备解码缓冲溢出后降级成占位图形——这就是切换页那个大圈。

判据只有一条硬指标：**解码像素数必须恰好等于 w×h，比值 1.00，槽位零剩余字节**。官方 14 个包（TicTacToe / LuaCalculator / Monika / Stride 等）全部是 52,996B 解 94,080 px，这条标准是从官方样本反推出来的，不是我们自己定的。

`tools/check_preview.py` 就是这个判据的批量化：一条命令体检整个 `dist/`，非 1.00 直接标坏。

## 五、可靠性评估（重点）

### 5.1 它可靠的部分：结构层，百分百

- **是不是能解**：解码器与固件同语义，解不出来就是坏的。
- **像素数对不对**：`w*h` 精确比对，1 px 都不放过。这正是大圈 bug 的判据。
- **表头是否自洽**：宽高、槽位长度、RLE 头三者能互相印证。
- **缩略图会不会退化成占位图形**：只要比值 1.00，这一类故障就可以排除。

这一层的可靠性来自「同源」：我们解的字节，就是固件解的那段字节，中间没有任何转译或近似。

### 5.2 它不可靠的部分：表现层，基本为零

必须说清楚一件事：**预览块是我们自己在出包时合成进包的，它不是 lua 渲染出来的。**

`tools/build_aurora.py` 里的 `compose_preview()` 是用 PIL 按 lua 的版式常量**另画了一张图**，再编码进包里。这意味着：

- 它验证的是「我声明给设备的缩略图合法」，**不是**「lua 跑起来会画成这样」。
- lua 里的版式改了而 `compose_preview` 没跟着改，两者就会**漂移**，而包依然是「健康」的。实例：v1.0.15 的缩略图左下角水印还写着 `v1.0.2`，体检照样 1.00 通过。
- 字体回退、文本换行、图片资源缺失、控件遮挡、事件（长按/点击）失效、内存溢出崩溃——**一个都测不出来**。这些只有真机跑了才知道。

所以这张图能当「预览」用，但定位要摆正：**它是缩略图的自证，不是表盘的预览**。

### 5.3 与其它几种预览方式对比

| 方式 | 得到什么 | 能发现大圈 | 能发现版式错 | 能发现运行时错 | 成本 |
|---|---|---|---|---|---|
| **解包内预览块** | 设备将显示的缩略图（像素级一致） | ✅ | ⚠️ 仅限「我们声明的那版」 | ❌ | 极低，一条命令 |
| 装机后手环实拍 | 真实盘面 | ✅（切换页可见） | ✅ | ✅ | 高，要设备+人眼 |
| 模拟器跑 lua | 真实渲染 | ❌ 模拟器不复现该降级 | ✅ | ✅ | 中，要起环境 |
| 自绘 HTML/PNG 效果图 | 设计意图 | ❌ | ❌ | ❌ | 极低但没证据力 |

结论：**解包内预览块 + `check_preview` 应当作为出包门禁（自动跑）；真机实拍作为发布前的人工验收（每次都做）。两者不能互相替代。**

### 5.4 什么情况下这个手段会骗你

1. **包是我们自己拼的，且合成预览与 lua 各写一套** → 版式漂移（已发生：水印版本号过期）。
2. **`encode_exact` 写错但恰好像素数对上** → 理论上极低概率，因为出口断言同时校验长度与像素数。
3. **表头宽高被改成一个「刚好能除尽」的错值** → 比值仍是 1.00，但图像会错行。防法：宽高必须硬断言等于 192×490（`build_aurora.py` 里已经这么做了）。
4. **只看图不看数字** → 人眼对「轻微错行」「末位缺字」不敏感，但数字会立刻暴露。

### 5.5 一句话总结

> **靠谱，但只靠谱在「这块数据合法吗」这一问上。**
> 它是防大圈的唯一有效手段，也是唯一能在不装机的情况下拿到设备缩略图的途径；
> 但它证明不了表盘好不好看、跑得对不对。任何「我看过预览图了所以没问题」的说法，都属于把结构体检当成了效果验收。

## 六、固化建议

1. **出包即断言**（已实现）：`build_aurora.py` 保存后立刻回读，`解码 px == 192*490` 且 `w,h == 192,490`，不满足直接 `AssertionError`，不产出文件。
2. **批量门禁**（已实现）：`python3 tools/check_preview.py dist/`，比值非 1.00 一律不出包、不装机。
3. **待补**：`compose_preview` 的版式常量应与 `main.lua` 同源（至少版本号、课程行文案从同一份数据生成），避免漂移——这是本次实测暴露的真实缺陷。
4. **待补**：解预览图这件事本身可以固化成 `tools/preview_png.py <face> -o out.png`，现在还是临时脚本，每次要手敲。

---

## 七、踩过的坑（留给下一个人）

- **别对字形 PNG 做二次 `magick` 重编码来「压小」**：146B 的 PaletteAlpha 图经 `-colors 8 -define png:color-type=3 PNG8:` 会退化成 Bilevel 8bit，体积涨到 325B，越压越大。
- **槽位是定长等长替换**，`inject_resource` 不允许超出容量；分配要用「体积降序 + best-fit」，否则大图先占中号槽，小图最后无槽可用。
- **最小槽位可能就是瓶颈**：`1.png` 只有 276B、`4.png` 357B、`7.png` 345B。字形 358B 时差 1 字节就永远分不出去，字格从 34×72 降到 30×62 才落进来。
- **`PingFang.ttc` 用 PIL 打不开**（`OSError: cannot open resource`），合成预览要准备字体回退链（本机可用 Hiragino Sans GB / STHeiti）。
- **预览槽里的 `mao.png` 就是冒号**，不是错别字，也不是缺失资源。
